# Клієнт-серверний режим: дизайн синхронізації

Статус: чернетка для рев'ю · оновлено 2026-10-04
Основа: обговорення 2–3 жовтня 2026, рішення зведено в розділі 2.

---

## 1. Мета

Desktop-додаток на Avalonia (.NET 10) з SQLite і EF Core отримує клієнт-серверний режим. Один клієнт підключається до кількох віддалених інстансів одночасно і працює з їхніми даними як зі своїми: фільтрує, сортує, створює, редагує, імпортує, видаляє.

Канал до інстансів може бути слабким і з великим latency, тому клієнт тримає локальну репліку кожного інстансу і працює з нею. Зміни користувача застосовуються локально одразу і доїжджають до власника у фоні, коли той доступний.

**Критерії успіху**

- Користувач не чекає мережу на жодну дію з даними. Відкрита таблиця з фільтром показує результат одразу з локальної репліки.
- Після перерви найсвіжіші дані з'являються першими, а стан синхронізації видно.
- Трафік пропорційний кількості змінених записів, а не кількості подій: сто змін одного запису передаються один раз.
- Невідправлені зміни видно в UI, і вони не губляться при обриві, перезапуску чи перезавантаженні репліки.

## 2. Прийняті рішення

| Тема | Рішення |
|---|---|
| Хто власник | Віддалений інстанс це той самий додаток, можливо headless. Він піднімає gRPC-сервер на ip:port. |
| Скільки інстансів | До ~10 на клієнта, стелі в дизайні нема. Один клієнт на власника для початку, дизайн допускає кілька. |
| Хто ініціює з'єднання | Завжди клієнт. gRPC-сервер є тільки на власнику, власник ніколи не підключається до клієнта і шле зміни через потік, який відкрив клієнт. |
| Мережа | Пряме з'єднання, мережа довірена. TLS і автентифікації в першій версії нема, gRPC дозволяє додати пізніше. |
| Версії | Клієнт і власник на одній версії додатку. Перше повідомлення потоку Subscribe перевіряє версію схеми. |
| Операції з клієнта | Повний CRUD та імпорт у віддалений інстанс. Зміни застосовує власник. |
| Ручне редагування на власнику | Вимкнене. На власнику пише тільки автоматика додатку. Усі ручні дії йдуть з клієнта. |
| Офлайн | Клієнт пише в репліку одразу і ставить дію в чергу. Черга відправляється, коли власник доступний. UI показує, що очікує відправки. |
| Конфлікт у колонці | Виграє той, хто останнім доїхав до власника. Автоматика може перезаписати ручну правку наступним проходом. |
| Видалення | Виграє над усім. Новий запис, батька якого власник видалив, відкидається. |
| Масове видалення | Тільки з клієнта, у headless його нема. Передаються ключі, які бачив користувач, а не фільтр. |
| PK | Автоінкремент прибираємо. Усі PK стають GUID. |
| FK | Є, глибокі ланцюжки A → B → C в обсязі дизайну. |
| Рівень реплікації | Рядковий: останній стан запису, tombstones для видалень, курсор версії. Оновлення від власника до клієнта їдуть поколонково: тільки колонки, змінені після версії, яку клієнт уже має (5.2, 6.4). Від клієнта до власника патч колонок, як і раніше. |
| Запис на власнику | EF Core: SaveChanges плюс ExecuteUpdate / ExecuteDelete. Тому зміни ловлять тригери SQLite, а не EF. |
| Сховище на клієнті | Окремий SQLite-файл на інстанс, це знімок власника з тією ж схемою. Читання через шар злиття. |
| Пагінація в UI | Перші N і довантаження при прокрутці. |
| Відставання понад термін зберігання | Клієнт перезавантажує знімок цілком. Невідправлені дії зберігаються. |
| Лічильник версій | Один на БД власника, 64-бітний. Курсори на клієнті окремі по таблицях, але це позиції в одній послідовності. |
| Звільнення місця на власнику | На вимогу користувача дані переносяться в архів клієнта і видаляються на власнику (розділ 11). |

## 3. Що не входить у першу версію

- Фільтр, переданий власнику для пріоритетної досинхронізації ("спосіб Б"). Перша версія пріоритезує відкриті таблиці цілком.
- Окремий запит "свіжі версії рядків, що на екрані" за ключами.
- TLS, автентифікація, relay через NAT.
- Ручне редагування на власнику і злиття правок двох людей з перевіркою base version.
- Пагінація стрибком у середину набору.
- Дві пачки Apply у польоті з окремим простором `seq` для інтерактивних дій (8.5).

## 4. Архітектура

```
        КЛІЄНТ                                  ВЛАСНИК (скільки завгодно)
┌───────────────────────────┐             ┌──────────────────────────┐
│ UI                        │             │ Автоматика додатку       │
│  │ читання     │ запис    │             │  │ EF Core               │
│  ▼             ▼          │             │  ▼                       │
│ Шар злиття   WriteRouter  │             │ SQLite БД власника (WAL) │
│  │   │   │     │          │             │  + SyncVersion у рядках  │
│  ▼   ▼   ▼     ▼          │             │  + тригери               │
│ local.db  A.db  B.db ...  │             │  + _sync_* таблиці       │
│           + курсори       │    gRPC     │  ▲            │          │
│           + черга дій     │◄───────────►│ SyncService              │
│              ▲            │             │  Snapshot,               │
│ SyncAgent A ─┘            │             │  Subscribe, Apply        │
│ SyncAgent B  (на інстанс) │             └──────────────────────────┘
└───────────────────────────┘
```

**Власник**
- Тригери на кожній таблиці, що реплікується, ставлять рядку нову `SyncVersion` і ведуть tombstones. Вони ловлять будь-який шлях запису: SaveChanges, ExecuteUpdate/Delete, імпорт, сирий SQL.
- SyncService працює в тому ж процесі. Читає БД власними з'єднаннями в режимі WAL і не блокує автоматику. Пише тільки в Apply, короткими транзакціями.
- Фонова задача очищення tombstones.

**Клієнт**
- **Репліка**: файл на інстанс, отриманий знімком. Та сама схема і той самий DbContext. У тому ж файлі курсори і черга дій, тож правка і запис у чергу це одна транзакція. Забути інстанс означає видалити файл.
- **SyncAgent**: по одному на інстанс. Автомат станів: нема зв'язку → handshake → знімок, якщо репліки нема або вона застаріла → потік змін (досинхронізація, далі онлайн) паралельно з відправкою черги.
- **Шар злиття**: виконує запит паралельно на local.db і всіх репліках, зливає відсортовані набори, обрізає до N. Кожен рядок позначений інстансом.
- **WriteRouter**: за інстансом рядка знаходить репліку, пише в неї і в тій же транзакції додає дію в чергу.

У кожного файлу свій writer, тому агенти різних інстансів і правки користувача не заважають одне одному.

## 5. Модель даних

### 5.1 Первинні ключі

- Усі таблиці, що реплікуються, мають PK типу GUID. Генерується в коді, рекомендую `Guid.CreateVersion7()`: він впорядкований за часом і дає кращу локальність індексу, ніж випадковий v4.
- GUID ніколи не перевикористовується. Це дозволяє вважати tombstone остаточним.
- Існуючі БД з автоінкрементом мігруються одноразово, див. розділ 15.

### 5.2 БД власника

**Колонка версії в кожній таблиці, що реплікується**

```sql
ALTER TABLE T ADD COLUMN SyncVersion INTEGER NOT NULL DEFAULT 0;
CREATE INDEX IX_T_SyncVersion ON T(SyncVersion);
```

- Додається EF-міграцією як shadow property, щоб EF знав про колонку і не загубив її при перебудові таблиці.
- EF ніколи не пише цю колонку: вона позначається як згенерована базою (`ValueGeneratedOnAddOrUpdate`), а таблиця оголошує тригери через `ToTable(t => t.HasTrigger(...))`, інакше EF використає `RETURNING`, що несумісне з тригерами в SQLite.
- Окремої таблиці змін для живих записів нема. Версія лежить у самому рядку, тож чистити нічого. Потік змін це `WHERE SyncVersion > курсор`.

**Поколонкові оновлення: база і маска.** Щоб зміна однієї колонки не тягнула весь рядок, кожна таблиця, що реплікується, має ще дві колонки:

```sql
ALTER TABLE T ADD COLUMN SyncBase INTEGER NOT NULL DEFAULT 0;  -- версія, стан на яку є в усіх активних клієнтів
ALTER TABLE T ADD COLUMN SyncMask INTEGER NOT NULL DEFAULT 0;  -- бітова маска колонок, змінених після SyncBase
```

- Вставка: `SyncBase = 0`, маска повна. Повна маска означає "рядок треба віддавати цілком".
- Оновлення: тригер дивиться на `floor` таблиці, тобто мінімальний курсор цієї таблиці серед **активних** клієнтів (`_sync_floor`, нижче). Якщо `floor ≥ OLD.SyncVersion`, попередню версію рядка вже мають усі активні клієнти: `SyncBase = OLD.SyncVersion`, маска = змінені колонки. Інакше база лишається, а змінені колонки додаються до маски (`SyncMask | змінені`).
- Інваріант: курсор кожного активного клієнта по таблиці не менший за `SyncBase` будь-якого її рядка, бо базу зсувають тільки на версію, яку бачили всі, а курсори лише ростуть. Тому активний клієнт завжди отримує лише колонки з маски, хоч би скільки разів рядок змінився.
- Маска це `INTEGER`, тобто до 63 колонок, порядок бітів за EF-моделлю; для ширших таблиць `BLOB`. Маска може містити колонки, які клієнт уже має (вони накопичились для іншого клієнта): це зайві байти, не помилка.
- Активний клієнт це той, хто був на зв'язку протягом вікна активності, за замовчуванням 24 години. Клієнт поза вікном не стримує базу; коли повертається, `SyncBase` рядків може бути вищою за його курсор, і він отримує повні рядки, як до цієї оптимізації. Клієнт, що довго офлайн у межах вікна, гальмує зсув бази, і маски ростуть для всіх, у гіршому разі до повного рядка, тобто не гірше, ніж без масок.

**Чому не журнал змін на власнику.** Альтернатива це outbox на власнику: рядок на кожне оновлення з маскою, очищення як для tombstones, об'єднання масок при відправці. Він дає виграш тільки клієнтам, що відстали, а саме там економія найменша, бо рядок за цей час зазвичай змінювався в багатьох колонках. База і маска в рядку покривають головний випадок, онлайн-клієнта біля голови, без другої таблиці.

**Які таблиці реплікуються.** Усі, дані яких користувач має бачити або змінювати з клієнта. Не реплікуються: локальні налаштування інстансу, шляхи, облікові дані, кеші й тимчасові таблиці, внутрішні логи, `__EFMigrationsHistory`. Конкретний перелік складається по DbContext (відкрите питання 1).

**Службові таблиці**

```sql
-- один рядок: хто я, лічильник версій, межа очищення
CREATE TABLE _sync_meta (
  instance_id     TEXT    NOT NULL,
  version         INTEGER NOT NULL,
  purged_version  INTEGER NOT NULL DEFAULT 0   -- найбільша версія видаленого tombstone
);

-- видалені записи
CREATE TABLE _sync_tombstones (
  tbl        TEXT    NOT NULL,
  pk         TEXT    NOT NULL,
  version    INTEGER NOT NULL,
  deleted_at INTEGER NOT NULL,                 -- unix-час власника
  PRIMARY KEY (tbl, pk)
) WITHOUT ROWID;
CREATE INDEX IX_sync_tombstones_version ON _sync_tombstones(tbl, version);
CREATE INDEX IX_sync_tombstones_deleted ON _sync_tombstones(deleted_at);

-- відомі клієнти
CREATE TABLE _sync_clients (
  client_id     TEXT    PRIMARY KEY,
  acked_version INTEGER NOT NULL,              -- мінімальний курсор клієнта по всіх таблицях
  applied_seq   INTEGER NOT NULL,              -- остання застосована дія клієнта
  last_seen     INTEGER NOT NULL
);

-- курсори клієнтів по таблицях, з Ack
CREATE TABLE _sync_client_cursors (
  client_id TEXT    NOT NULL,
  tbl       TEXT    NOT NULL,
  cursor    INTEGER NOT NULL,
  PRIMARY KEY (client_id, tbl)
) WITHOUT ROWID;

-- мінімальний курсор активних клієнтів по таблиці; читає тригер оновлення
CREATE TABLE _sync_floor (
  tbl   TEXT    PRIMARY KEY,
  floor INTEGER NOT NULL
) WITHOUT ROWID;
```

`_sync_floor` перераховується при кожному `Ack` і при зміні складу активних клієнтів (клієнт випав з вікна активності): `floor = MIN(cursor)` серед активних, а без жодного активного клієнта `floor` = голова версій, і база зсувається на кожному оновленні. Тригер читає одне значення за первинним ключем, тож на швидкість запису це майже не впливає.

`purged_version` це доповнення до погодженої схеми: без нього власник не може відрізнити клієнта, якому вистачить досинхронізації, від клієнта, якому потрібен новий знімок (розділ 10).

**Тригери на кожну таблицю.** Генеруються з EF-моделі і перестворюються при кожному старті після міграцій, бо перебудова таблиці в SQLite їх знищує.

```sql
CREATE TRIGGER _sync_T_ins AFTER INSERT ON T BEGIN
  UPDATE _sync_meta SET version = version + 1;
  UPDATE T SET SyncVersion = (SELECT version FROM _sync_meta),
               SyncBase = 0, SyncMask = <повна маска T>
  WHERE Id = NEW.Id;
  DELETE FROM _sync_tombstones WHERE tbl = 'T' AND pk = NEW.Id;
END;

CREATE TRIGGER _sync_T_upd AFTER UPDATE ON T
WHEN NEW.SyncVersion = OLD.SyncVersion BEGIN
  UPDATE _sync_meta SET version = version + 1;
  UPDATE T SET
    SyncVersion = (SELECT version FROM _sync_meta),
    SyncBase = CASE WHEN (SELECT floor FROM _sync_floor WHERE tbl = 'T') >= OLD.SyncVersion
               THEN OLD.SyncVersion ELSE OLD.SyncBase END,
    SyncMask = CASE WHEN (SELECT floor FROM _sync_floor WHERE tbl = 'T') >= OLD.SyncVersion
               THEN <змінені> ELSE OLD.SyncMask | <змінені> END
  WHERE Id = NEW.Id;
END;
-- <змінені> генерується з EF-моделі:
--   (OLD.c1 IS NOT NEW.c1) * 1 | (OLD.c2 IS NOT NEW.c2) * 2 | ... (службові колонки Sync* не рахуються)

CREATE TRIGGER _sync_T_del AFTER DELETE ON T BEGIN
  UPDATE _sync_meta SET version = version + 1;
  INSERT OR REPLACE INTO _sync_tombstones(tbl, pk, version, deleted_at)
  VALUES ('T', OLD.Id, (SELECT version FROM _sync_meta),
          CAST(strftime('%s','now') AS INTEGER));
END;
```

- Умова `WHEN` не дає тригеру на update спрацювати на власне оновлення версії, бази і маски.
- Порівняння `OLD.c IS NOT NEW.c` на кожну колонку це додаткова робота на кожен update; для ExecuteUpdate на 100k рядків вона помітна, і її теж міряє перший крок плану (розділ 16).
- Кожен рядок отримує унікальну версію. Оскільки writer у SQLite один, порядок версій збігається з порядком комітів, і "дай усе після N" ніколи не пропускає запис.
- Каскадні видалення по FK теж запускають тригер на delete, тому tombstones отримують і дочірні записи. Це треба підтвердити тестом на реальній схемі.

**Режим WAL** вмикається, якщо ще не ввімкнений. Разом з ним `auto_vacuum = INCREMENTAL`, щоб після видалень можна було повертати місце на диск без повного VACUUM (розділ 11.5).

### 5.3 Лічильник версій

**Один лічильник на БД, а не на таблицю.** Курсори в `_sync_cursors` окремі по таблицях, але вони вказують позицію в одній спільній послідовності: запит `WHERE SyncVersion > cursor` по таблиці T просто пропускає версії, що дісталися іншим таблицям. Окремий лічильник на таблицю нічого не дає, а забирає три речі:

- **Порядок між таблицями.** Батько і дочірній запис, створені в одній транзакції, отримують сусідні версії. В онлайн-фазі власник шле зміни за зростанням спільної версії, тож батько приїжджає раніше за дитину. З окремими лічильниками цей порядок втрачається.
- **Одне число для порівнянь.** Версія знімка, `acked_version`, `purged_version` і перевірка "клієнт відстав" це одне число. З окремими лічильниками кожне з них стало б набором по таблицях.
- **Простота тригерів.** Конкуренції за рядок `_sync_meta` нема, бо writer у SQLite однаково один.

**Переповнення.** `INTEGER` у SQLite 64-бітний, максимум 9,2·10¹⁸. При 1000 змін за секунду його вистачить на 290 мільйонів років, при мільйоні змін за секунду на 290 тисяч. Самому лічильнику переповнення не загрожує. Реальних ризиків два:

1. **32-бітне число десь по дорозі.** `int` у C# або `int32` у proto переповнюються на 2,1·10⁹, а це близько 24 днів при 1000 змін за секунду. Правило: версія скрізь `long` у C# і `int64` у proto, включно з shadow property `SyncVersion`, курсорами, `seq` черги і `applied_seq`. Перевіряється тестом, який стартує лічильник з 2³¹ + 1.
2. **Версія пішла назад.** Якщо БД власника відновили з бекапу або підмінили файл, лічильник повертається до старого значення і далі видає версії, які клієнт уже вважає отриманими. Поки нова версія власника нижча за курсор клієнта, це ловить handshake. Але щойно власник наздожене курсор, клієнт мовчки пропустить зміни між ними. Захист:
   - власник при кожному коміті синку (або раз на кілька секунд) записує `instance_id` і поточну версію у файл поруч з БД, поза нею;
   - на старті, якщо версія в БД менша за записану в цьому файлі, БД відкотилась: власник генерує новий `instance_id`, і всі клієнти беруть новий знімок;
   - функція відновлення з бекапу в самому додатку завжди генерує новий `instance_id`.

Місце це не збільшує: SQLite зберігає цілі змінної довжини, тож версії до 2·10⁹ займають у рядку до 4 байт, до 1,4·10¹⁴ до 6 байт.

### 5.4 Репліка на клієнті

Репліка це знімок власника, тому все з 5.2 приїжджає разом з файлом. Після завантаження клієнт один раз перетворює файл на репліку:

- видаляє тригери синку: версії в репліці дзеркалять власника, а не ростуть самі;
- видаляє `_sync_tombstones` і `_sync_clients`;
- лишає `_sync_meta` як джерело `instance_id` і початкового курсора;
- додає свої таблиці.

```sql
-- до якої версії синхронна кожна таблиця
CREATE TABLE _sync_cursors (
  tbl         TEXT    PRIMARY KEY,
  cursor      INTEGER NOT NULL    -- усе <= cursor отримано
);

-- отримані відрізки версій вище за cursor, поки досинхронізація не завершена
CREATE TABLE _sync_ranges (
  tbl   TEXT    NOT NULL,
  lo    INTEGER NOT NULL,         -- відрізок (lo, hi]
  hi    INTEGER NOT NULL,
  PRIMARY KEY (tbl, hi)
) WITHOUT ROWID;

-- невідправлені дії користувача, один рядок на запис
CREATE TABLE _sync_outbox (
  id      INTEGER PRIMARY KEY AUTOINCREMENT,   -- порядок створення, тільки локальний
  seq     INTEGER UNIQUE,         -- номер для власника; NULL до першої відправки (8.5)
  tbl     TEXT    NOT NULL,
  pk      TEXT    NOT NULL,
  kind    INTEGER NOT NULL,       -- 1 створення, 2 патч, 3 видалення, 4 перенесення в архів, 5 масова дія за предикатом
  cls     INTEGER NOT NULL,       -- 1 інтерактивна, 2 масова (8.5)
  columns TEXT,                   -- для патча: список змінених колонок
  predicate TEXT,                 -- для масової дії: серіалізована умова і версія V (8.6)
  expected_version INTEGER,       -- для перенесення по ключу: версія, яку скопійовано в архів
  sent    INTEGER NOT NULL DEFAULT 0,
  UNIQUE (tbl, pk)
);
```

Курсор таблиці означає "усі версії до цієї я отримав", а не "версія мого останнього рядка": оскільки лічильник спільний, у спокійної таблиці курсор рухається разом з головою власника, хоч її рядки не їздять (6.4, "Порожні проміжки").

`seq` присвоюється не при створенні дії, а при першій відправці, з лічильника, що зростає з кожною відправленою дією; повторна відправка йде з тим самим `seq`. Так власник завжди отримує `seq` у зростаючому порядку, хоч би в якому порядку агент вибирав дії з черги (8.5).

`_sync_ranges` і `sent` це доповнення до погодженої схеми. Перша дозволяє продовжити перервану досинхронізацію з того ж місця і при цьому завжди віддавати найновіше першим (6.4). Друге потрібне, щоб правка запису, дія якого вже в дорозі, не загубилась (8.3). Коли таблиця досинхронізована, у `_sync_ranges` для неї рядків нема: усе отримане злилось у `cursor`.

У черзі нема значень, тільки "що зроблено і з якими колонками". Значення агент читає з рядка репліки в момент відправки, тож завжди їде останній стан, і схлопування виходить само.

**Місцевий стан на клієнті поза реплікою**: `client_id` (один на інсталяцію клієнта) і список підключених інстансів з адресами зберігаються в local.db.

## 6. Протокол

### 6.1 Сервіс

```proto
service Sync {
  rpc Snapshot  (SnapshotRequest)  returns (stream SnapshotChunk);
  rpc Subscribe (stream SubscribeMessage) returns (stream ChangeMessage);
  rpc Apply     (ApplyRequest)     returns (ApplyReply);
}
```

Ініціатор завжди клієнт: усі три виклики відкриває він, у тому числі довгий потік Subscribe, через який власник шле зміни в онлайн-режимі. Власнику не потрібно знати адресу клієнта, і клієнт може бути за NAT. Якщо потік обірвався, перепідключається клієнт.

Канал стискається на рівні gRPC (gzip у першій версії). На табличних даних це дає 3–5 разів.

**Вікно потоку HTTP/2.** Пропускна здатність одного потоку обмежена `вікно / RTT`. Зі стандартними 64 КБ при RTT 2,5 с це ~25 КБ/с, тобто близько 10 % каналу на 2 Мбіт/с: за симуляцією година офлайну при 100 рядків/с досинхронізується 31 хв або не закінчується, з вікном ~1 МБ за 1,5 хв. Тому вікно задається явно, не менше за `пропускна здатність × RTT` (для 2 Мбіт/с і 3 с це ~1 МБ): на власнику `Kestrel Http2.InitialStreamWindowSize` і `InitialConnectionWindowSize`, на клієнті `SocketsHttpHandler.InitialHttp2StreamWindowSize`. Динамічне масштабування вікна в .NET є, але покладатись на нього можна тільки після перевірки на стенді (розділ 16).

### 6.2 Handshake: перше повідомлення Subscribe

Окремого методу Handshake нема: встановлення зв'язку (TCP, TLS, перший обмін) коштує 3–5 RTT, тобто 8–12 с при RTT 2,5 с, і кожен зайвий обмін до першої пачки це ще один RTT. Тому handshake це перше повідомлення `Start` у потоці Subscribe. Воно несе `client_id`, версію схеми, `instance_id` репліки (якщо є), курсори з відрізками і список відкритих таблиць. Власник відповідає одразу в тому ж потоці:

| Відповідь | Коли | Що робить клієнт |
|---|---|---|
| перша пачка | схема та сама, `instance_id` збігається, мінімальний курсор ≥ `purged_version` | застосовує і паралельно починає Apply |
| `SnapshotRequired`, потік закривається | репліки нема, інший `instance_id` (БД власника замінили) або курсор < `purged_version` | спершу відправляє чергу, потім знімок або порожня репліка (6.3, 10.3) |
| `SchemaMismatch`, потік закривається | версії схеми різні | інстанс у статусі "несумісна версія", черга зберігається |

Власник оновлює `last_seen` клієнта. Потік живе між обривами скільки завгодно, тож ця ціна платиться раз на обрив.

### 6.3 Snapshot

- Власник робить `VACUUM INTO` у тимчасовий файл. Це цілісний знімок на момент початку читання, і він не блокує writer-а. `_sync_meta.version` у файлі дає версію знімка V.
- У тій же операції власник реєструє клієнта в `_sync_clients` з `acked_version = V`, щоб очищення не видалило tombstones, які клієнту знадобляться одразу після знімка.
- Файл віддається потоком шматків по ~1 МБ зі зміщенням. Після обриву клієнт просить продовження з того ж зміщення за `snapshot_id`. Власник тримає тимчасовий файл кілька годин або до завершення завантаження.
- Клієнт перевіряє хеш, перетворює файл на репліку (5.4), ставить усім курсорам V і атомарно підміняє старий файл новим.

**Файл чи порожня репліка.** Поки файл їде, інстанс для користувача порожній: за симуляцією 1 млн рядків (50 МБ стиснуто) на 2 Мбіт/с це 3,4 хв, 5 млн це 17 хв. Файл не можна віддати "від нових до старих", але є еквівалент: клієнт створює порожню репліку зі схемою (міграції додатку), ставить усі курсори в 0 і йде звичайним потоком Subscribe, який і так віддає нові першими з пріоритетом відкритих таблиць. Свіжі дані видно за секунди, хвіст доїжджає у фоні. Рядковий потік на 20–40 % важчий за стиснутий файл, тому повна репліка з'являється пізніше, ніж з файлу.

Правило: якщо `розмір знімка / виміряна швидкість каналу` менше за **5 хвилин**, файл; інакше порожня репліка. Розмір знімка власник повідомляє у `SnapshotRequired`. Користувач може перемкнути вибір вручну.

**Кілька інстансів одночасно.** Агенти не тягнуть знімки паралельно: паралельне завантаження ділить канал порівну, і всі інстанси стають доступними одночасно пізно (10 інстансів по 1 млн рядків це 33 хв до першого). Знімки йдуть по черзі, спершу інстанс, відкритий в UI; досинхронізація решти в цей час теж чекає. Онлайн-потоки вже синхронних інстансів не зупиняються.

### 6.4 Subscribe: досинхронізація і онлайн

Один двонаправлений потік на інстанс. Клієнт нічого не опитує.

**Повідомлення клієнта**
- `Start`: курсори по таблицях разом з отриманими відрізками з `_sync_ranges`, список відкритих зараз таблиць.
- `OpenTables`: список відкритих таблиць змінився.
- `Ack`: курсори після застосування. Власник зберігає їх у `_sync_client_cursors`, `acked_version = min(cursor)` у `_sync_clients` і перераховує `_sync_floor`, не частіше ніж раз на кілька секунд. Разом з `Ack` може йти список `NeedFull(tbl, pk)`: рядки, для яких клієнт отримав часткове оновлення, але не має самого рядка (7).

**Повідомлення власника**
- `Batch`: таблиця, межі покритого проміжку версій (gap_lo, gap_hi], перелік колонок один раз, далі рядки і tombstones (pk, version). Рядків може бути нуль: проміжок усе одно вважається отриманим. Рядок іде в одній з двох форм:
  - **повний**: pk, `SyncVersion`, усі колонки;
  - **частковий**: pk, `SyncVersion`, маска, значення тільки колонок з маски.

**Повний чи частковий.** Для кожного рядка проміжку власник вирішує окремо, за курсором саме цього клієнта по таблиці ("усе ≤ V отримано", а не межі запитаного проміжку, бо вище за курсор є діри):
  - маска повна (вставка, або рядок вставлено після бази) → повний;
  - `курсор клієнта ≥ SyncBase` → частковий: у клієнта є стан рядка на базу, і колонок з маски достатньо;
  - інакше (клієнт був поза вікном активності, база пішла вперед без нього) → повний.
  Видалення лишаються tombstones. Запит "дай зміни 100–120" таким чином повертає нові рядки цілком, а змінені тільки зміненими колонками.
- `TableSynced(tbl, V)`: діапазон досинхронізації таблиці вичерпано, курсор = V.
- `Head(V)` в онлайн-режимі: усі таблиці потоку повні до версії V.
- Будь-яке повідомлення власника може нести список `extra` з відрізків (tbl, lo, hi], які виявились порожніми: клієнт закриває їх тим самим правилом злиття.
- `Progress`: оцінка, скільки змін лишилось по кожній таблиці, і час власника, до якого дані синхронні.

**Досинхронізація.** Стан таблиці на клієнті це курсор C (усе ≤ C отримано) і список отриманих відрізків (lo, hi] вище за C. Невідправлене це все, що вище за C і не входить у жоден відрізок. Правило одне, і воно діє незалежно від того, скільки встигло з'явитись на власнику: **власник завжди шле найвищі невідправлені версії, від нових до старих**.

Перед кожною пачкою власник бере поточну голову H = `_sync_meta.version` і знаходить верхню прогалину: від H донизу до верхньої межі найвищого відрізка, або до C, якщо відрізків нема. З неї йде пачка:

```sql
SELECT * FROM T
WHERE SyncVersion > @gap_lo AND SyncVersion <= @gap_hi
ORDER BY SyncVersion DESC LIMIT @n;
```

плюс tombstones таблиці з того ж проміжку, злиті за версією.

- Клієнт після застосування пачки додає відрізок (min версій пачки, gap_hi] і одразу зливає його з сусідами: відрізок, який торкнувся верхньої межі нижчого, зливається з ним, а відрізок, що торкнувся C, зникає, і C піднімається до його hi. Усе це в тій же транзакції, що й застосування пачки.
- Порядок таблиць: спершу відкриті, разом з таблицями, на які вони посилаються по FK, далі решта. `OpenTables` посеред потоку змінює порядок з наступної пачки.
- Нові записи мають найвищі версії, тому в списку, відсортованому за датою спадно, верх заповнюється першим.
- Рядок, змінений під час досинхронізації, отримує версію вище за будь-який відрізок і потрапляє у верхню прогалину, тобто в наступну пачку. Чекати на нього до кінця хвоста не треба.
- Після обриву клієнт передає курсор і відрізки у `Start`, і власник продовжує з тієї ж прогалини. Нічого не тягнеться повторно, скільки б обривів не було.
- `TableSynced(T, H)` надсилається, коли на момент перевірки прогалин нема: єдиний відрізок дійшов до C і злився з ним. Після цього таблиця переходить в онлайн-режим.

**Порожні проміжки.** Лічильник версій спільний для всіх таблиць, тому у версіях окремої таблиці є діри: версії, які дістались іншим таблицям. Для таблиці, яка нічого не змінювала, проміжок (C, H] може бути порожнім цілком, і такий самий порожній хвіст з'являється щоразу, коли змінюються інші таблиці. Якби курсор рухався тільки за отриманими рядками, він застряг би на версії останньої власної зміни, а `acked_version = min(cursor)` разом із ним: очищення tombstones зупинилося б, а після паузи handshake порівняв би старий курсор з `purged_version` і вимагав би знімок без жодної причини. Тому курсор відображає не "останню отриману зміну", а "до якої версії я повний":

- кожен `Batch` несе межі проміжку, який він покриває. Клієнт записує весь проміжок як отриманий, навіть якщо рядків у ньому менше за розмір пачки. Пошук по індексу `SyncVersion` у порожньому проміжку це одне звернення до індексу, тож перевіряти порожні проміжки майже безкоштовно;
- але окремих повідомлень для порожніх проміжків власник не шле: інакше під час досинхронізації він витрачав би кожне коло на порожні `Batch` для спокійних таблиць, і таблиця з реальним хвостом голодувала б. Власник закриває порожні проміжки у себе і додає їх списком `extra` до наступного повідомлення, яке й так іде клієнту (`Batch`, `TableSynced`, `Progress`). Клієнт застосовує їх тим самим правилом "додати і злити";
- `TableSynced` надсилається один раз, коли таблиця вперше стала без прогалин, а не на кожен зсув голови;
- в онлайн-режимі власник після кожного кола по таблицях шле `Head(V)`, і клієнт піднімає до V курсори всіх таблиць, у яких нема відкритих відрізків. Так курсор спокійної таблиці тримається біля голови, хоч її рядки давно не їздили.

**Скільки відрізків накопичується.** Поки зміни на власнику з'являються повільніше, ніж їх забирає канал, відрізок один: кожна пачка нарощує його донизу, а те, що з'явилось зверху, це кілька рядків, які зливаються з ним за одну пачку. Відрізків стає кілька лише коли за час однієї пачки на власнику з'явилось більше рядків, ніж вміщує пачка. Тоді кожна пачка бере новий шматок з голови і не дотягується до попереднього, і список росте на один за пачку.

Ліміту на кількість відрізків нема: правило "найновіше першим" діє завжди, а список сам стискається, щойно навантаження спадає нижче за канал, бо тоді кожна пачка дотягується до попереднього відрізка і зливає їх. Симуляція показала, що ліміт з добиванням старого шматка тільки відкладає появу нових рядків (1,5–3 хв замість секунд), не даючи нічого натомість.

Ціна відсутності ліміту: за стійкого перевантаження список росте приблизно на один відрізок за пачку, тобто кілька за секунду. За годину це десятки тисяч пар чисел, і `Start` після обриву з такою кількістю відрізків на каналі 70 кбіт/с іде десятки секунд. Тому відрізки у `Start` кодуються компактно (різниці між сусідніми межами, varint), а як запобіжник є верхня межа порядку 10 000 відрізків на таблицю, яка за реального навантаження не досягається; на ній власник добиває найвищий відрізок, як описано для ліміту раніше. Це запобіжник від зростання стану, а не елемент поведінки.

**Якщо зміни стабільно з'являються швидше за канал.** Тоді хвіст не рухається, бо кожна пачка йде на верхні прогалини, і репліка ніколи не стане повною. Жоден порядок обходу цього не виправить: канал пропускає менше, ніж створює автоматика. Що дизайн гарантує в цьому режимі:

- користувач бачить найновіші записи з затримкою в одну-дві пачки;
- обриви нічого не коштують, стан курсора обмежений;
- у статусі видно "відстаємо на N змін" і що N росте, а не стоїть, тобто це не пауза, а недостатня пропускна здатність.

Схлопування пом'якшує це для оновлень: рядок, змінений кілька разів, їде один раз. Для потоку нових записів допомагає тільки ширший канал або менше даних, наприклад винести важкі колонки в окремі таблиці, які клієнт не відкриває (відкрите питання 13).

**Онлайн.** Після досинхронізації всіх таблиць потік не закривається. Власник дізнається про нові коміти опитуванням `PRAGMA data_version` кожні ~250 мс (тригери не вміють сповіщати процес, а опитування цієї прагми майже безкоштовне) і шле "усе > останнього відправленого" за зростанням версій.

**Склеювання дрібних пачок.** Пачка з кількох рядків коштує ~200 байт на рядок після gzip проти ~50 у великій, і на обмеженому вікні потік таких пачок з'їдає канал: за симуляцією при 500 рядків/с і RTT 2,5 с p95 затримки 128 с, а досинхронізація стоїть. Тому власник шле онлайн-пачку не частіше ніж раз на 0,5 с (налаштування), збираючи все, що з'явилось; під час досинхронізації свіжий хвіст, менший за пачку, не чекає, а їде в тому ж повідомленні, що й пачка старого проміжку, як `extra`. Пачка досинхронізації не менша за ~64 КБ, щоб використовувати вікно цілком. Затримка для користувача зростає щонайбільше на півсекунди, це менше за RTT.

**Зворотний тиск.** Наступну пачку власник читає тільки після того, як попередню прийняв канал (`await WriteAsync`), і тримає в польоті не більше ніж `пропускна здатність × RTT` невідправлених байтів: вікно, більше за це, не прискорює потік, а ставить відповіді Apply і `Head` у чергу за даними (до 1,5 с у симуляції). Якщо клієнт не встигає, черга на власнику не росте: наступне читання знову бере актуальний стан, і проміжні зміни схлопуються самі. Онлайн плавно переходить у безперервну досинхронізацію.

### 6.5 Apply: відправка дій клієнта

```
ApplyRequest { client_id, actions: [ { seq, tbl, pk, kind, columns, values } ] }
ApplyReply   { applied_up_to_seq, results: [ { seq, status, reason } ] }
```

- Розмір пачки обмежений часом відправки, не кількістю дій: агент міряє швидкість останніх відправок і цілиться в ~15 с передачі, у межах 16 КБ–1 МБ (на 70 кбіт/с це ~128 КБ). Пачка на 1 МБ іде 2 хв, і при обривах раз на 2 хв імпорт 10k рядків дає p95 9 хв і 830 КБ повторно відправлених даних; пачки 64–256 КБ дають p95 4 хв.
- Пачка збирається спершу з інтерактивних дій (8.5), потім з масових, і закрита по залежностях: якщо дія посилається на запис, створення якого теж у черзі, це створення йде в тій самій або раніше відправленій пачці (8.4).
- У польоті одна пачка. Дві пачки одночасно (інтерактивна не чекає, поки доїде масова) заплановано на пізніше, див. 8.5.
- Власник застосовує пачку в одній короткій транзакції, з `PRAGMA defer_foreign_keys = ON`, щоб порядок дій усередині пачки не мав значення.
- Дії з `seq ≤ applied_seq` клієнта пропускаються як уже застосовані. `applied_seq` оновлюється в тій самій транзакції. Тому повторна відправка після втраченої відповіді безпечна.
- Семантика дій на власнику:

| Дія | Як застосовується | Результат |
|---|---|---|
| Створення | `INSERT ... ON CONFLICT(Id) DO UPDATE` усіма колонками | `Applied`; якщо pk є в tombstones, `Rejected: deleted` |
| Патч | `UPDATE T SET <перелічені колонки> WHERE Id = ?` | `Applied`; якщо рядка нема, `Ignored: deleted` |
| Видалення | `DELETE FROM T WHERE Id = ?`, каскад за схемою власника | `Applied` також коли рядка вже нема |
| Перенесення в архів | `DELETE FROM T WHERE SyncVersion <= ? AND <умова>` | `Applied` зі списком ключів, які не видалено, бо змінились після V (розділ 11) |
| Масове видалення за предикатом | `DELETE FROM T WHERE SyncVersion <= ? AND <умова>` | те саме; рядки, змінені після V, лишаються і повертаються списком |

- Перевірка FK явна, по моделі EF: для кожної FK-колонки створення або патча батько має існувати в БД або створюватися в цій же пачці. Інакше дія `Rejected: parent deleted`, і так само відкидаються дочірні створення з тієї ж пачки, що від неї залежать. Це пошук за PK, він дешевий, на відміну від `PRAGMA foreign_key_check` по таблиці з мільйонами рядків.
- Після застосування тригери власника ставлять нові версії, і зміни повертаються клієнту звичайним потоком Subscribe.

## 7. Застосування змін на клієнті

Агент пише в репліку пачками по кількасот рядків у транзакції, з `PRAGMA foreign_keys = OFF` на своєму з'єднанні, бо при пріоритетах дочірні рядки можуть приїхати раніше за батьків.

**Повний рядок з власника**

```sql
INSERT INTO T (...) VALUES (...)
ON CONFLICT(Id) DO UPDATE SET ... 
WHERE excluded.SyncVersion > T.SyncVersion;
```

**Частковий рядок з власника**

```sql
UPDATE T SET c3 = ?, c7 = ?, SyncVersion = ?
WHERE Id = ? AND SyncVersion < ?;
```

- Якщо рядка в репліці нема (власник вважав, що клієнт його має, а його нема, наприклад після збою посеред застосування), клієнт не вигадує рядок, а додає pk у `NeedFull` наступного `Ack`, і власник шле повний рядок як `extra`. Це аномалія, не звичайний шлях.
- Застосування ідемпотентне і не залежить від порядку: старіша версія ніколи не перезапише новішу. Для часткових рядків це так само, бо `SyncVersion` рядка порівнюється перед оновленням.
- Якщо для рядка є патч у `_sync_outbox`, перелічені в ньому колонки не перезаписуються, решта оновлюється. Якщо в черзі створення, рядок не чіпається взагалі, бо локальний стан новіший. Якщо в черзі видалення, рядок не вставляється.

**Tombstone з власника**
- `DELETE FROM T WHERE Id = ? AND SyncVersion < ?`.
- Якщо для запису є патч у черзі, видалення виграє: запис зникає, дія з черги видаляється, користувач отримує сповіщення "правку запису X втрачено: його видалено на інстансі".

**Після пачки** агент сповіщає UI: інстанс, таблиці, кількість змін. Відкрита таблиця перечитується одразу для спокійних таблиць і не частіше ніж раз на кілька секунд для шумних (список шумних таблиць задається в конфігурації).

**Цілісність.** Поки всі таблиці не досинхронізовані, у репліці можуть бути рядки без батька. UI має це переносити: показувати порожнє значення посилання, а не падати. Коли всі діапазони закриті, репліка цілісна.

## 8. Запис з клієнта

### 8.1 WriteRouter

Дія користувача над рядком інстансу X пишеться в репліку X звичайним DbContext. У тій же транзакції WriteRouter оновлює `_sync_outbox`:

- **SaveChanges**: дії і змінені колонки беруться з change tracker (`Added`, `Modified` з переліком властивостей, `Deleted`).
- **ExecuteUpdate**: спершу `INSERT INTO _sync_outbox ... SELECT Id FROM T WHERE <фільтр>` з колонками, які оновлюються, потім саме оновлення.
- **ExecuteDelete / видалення по фільтру**: так само, ключі вибираються тим самим фільтром у тій самій транзакції. Це рівно ті записи, які користувач бачив, а не те, що з'явиться у власника пізніше.
- **Імпорт**: звичайні створення, просто їх багато. Черга відправляється пачками.

`SyncVersion` нових локальних рядків 0, тож будь-яка версія з власника для цього рядка вважатиметься новішою, але правила 7 захищають його, поки дія в черзі.

### 8.2 Схлопування в черзі

| Було в черзі | Нова дія | Стає |
|---|---|---|
| нічого | будь-яка | ця дія |
| створення | патч | створення |
| створення | видалення | рядок черги видаляється, власник нічого не дізнається |
| патч | патч | патч з об'єднаним списком колонок |
| патч | видалення | видалення |

### 8.3 Дія, яка вже в дорозі

Якщо рядок черги має `sent = 1` і користувач знову змінює запис, старий рядок черги видаляється і вставляється новий (новий `id`, `seq` ще не присвоєний) з об'єднаною дією. Інакше відповідь на попередню відправку видалила б рядок черги разом з новою правкою, а повтор після втраченої відповіді власник пропустив би за `applied_seq`.

Тому створення на власнику це upsert (6.5): якщо перша відправка створення загубилась, а друга вже з іншим `seq`, запис усе одно з'явиться. Після `ApplyReply` агент видаляє рядки черги з `seq ≤ applied_up_to_seq`.

### 8.4 Ланцюжки FK

Офлайн створений ланцюжок A → B → C має доїхати цілісно.

- Під час збирання пачки агент для кожного створення чи патча з FK на запис, створення якого теж у черзі і ще не відправлене, додає це створення в пачку. Обхід транзитивний, за моделлю EF.
- Усередині пачки порядок неважливий завдяки `defer_foreign_keys`.
- Якщо власник відкинув A (батька видалено), він відкидає і B, і C. Клієнт видаляє відкинуті записи з репліки разом з дочірніми, прибирає їх з черги і показує список "не збережено: батьківський запис видалено".

### 8.5 Пріоритет інтерактивних дій

Канал вгору слабкий (70 кбіт/с це ~8,75 КБ/с, і TCP-підтвердження потоку вниз забирають ще частину). У черзі FIFO одна правка користувача після імпорту 10k рядків чекає ~3 хв, а під час досинхронізації ~5,5 хв. Тому дії в черзі мають клас:

- **інтерактивні**: SaveChanges з UI, тобто те, що користувач зробив руками і чекає побачити підтвердженим;
- **масові**: імпорт, ExecuteUpdate/ExecuteDelete, видалення по фільтру, перенесення в архів.

Черга лишається однією таблицею з колонкою `cls`. Агент збирає пачку спершу з інтерактивних дій незалежно від порядку створення, потім додає масові. Залежності по FK (8.4) тягнуть потрібні створення з масового класу в ту саму пачку, тому цілісність не ламається.

**Чому `seq` дається при відправці, а не при створенні.** Якби `seq` присвоювався при створенні, пріоритет ламав би захист від повторів: масова дія #40 ще в черзі, інтерактивна #50 іде першою, власник ставить `applied_seq = 50`, і наступна пачка з #40 пропускається як "уже застосована". Дія губиться мовчки. Тому в черзі є локальний порядок створення (`id`), а `seq` дія отримує в момент першої відправки з лічильника відправок, і повтори йдуть з тим самим `seq`. Власник отримує `seq` строго за зростанням, і одного `applied_seq` вистачає, поки в польоті одна пачка.

**Пізніше: дві пачки в польоті.** Щоб інтерактивна правка не чекала навіть на передачу поточної масової пачки, можна тримати дві пачки одночасно. Тоді власник може отримати інтерактивну дію раніше за масову з меншим `seq`, і одного `applied_seq` недостатньо. Рішення: інтерактивна черга має власний простір `seq` (окремий лічильник і окреме `applied_seq_interactive` у `_sync_clients`). Це відкладено, бо потребує другого лічильника в коді черги, а виграш це хвилина на пачку.

### 8.6 Масові дії за предикатом

Масове видалення 100k рядків ключами іде ~8 хв на каналі вгору, архів 100k з парами (ключ, версія) ~10 хв. Тому масова дія передається як предикат, коли фільтр користувача це можна виразити:

- Клієнт шле таблицю, умову (список значень, діапазон, кілька рівностей, тобто серіалізований простий фільтр) і версію V, до якої його репліка повна по цій таблиці (нема відрізків вище за курсор). Власник виконує `DELETE FROM T WHERE SyncVersion <= V AND <умова>`.
- Умова `SyncVersion ≤ V` і є перевіркою "не змінився після того, як клієнт його бачив", тільки для всього набору разом. Рядки, змінені після V, лишаються і повертаються списком ключів `Rejected: changed`; для архіву клієнт перекопіює їх і повторює, для видалення показує користувачу. У цей список потрапляють і рядки, створені після V, бо власник не відрізняє новий рядок від зміненого; повідомлення користувачу так і каже: "змінено або створено після того, як ви бачили дані".
- Каскади по FK виконує власник за своєю схемою, як і для видалення по ключу.
- Якщо фільтр складний (не серіалізується), лишається попередній спосіб: ключі, які бачив користувач, пачками.

Це не "фільтр на власнику" з розділу 3: власник видаляє рівно те, що клієнт уже бачив у версіях ≤ V, нічого нового під умову не потрапляє.

### 8.7 Каскади і FK на клієнті

З'єднання WriteRouter працює з `foreign_keys = ON`, щоб локальне видалення каскадом прибирало дочірні рядки так само, як прибере власник. У чергу йде тільки видалення батька, каскад власник зробить сам. Якщо локальна перевірка FK падає через рядок, батько якого ще не приїхав, користувач бачить "дані ще синхронізуються, спробуйте пізніше" (відкрите питання 6).

## 9. Конфлікти

| Ситуація | Результат |
|---|---|
| Клієнт і автоматика змінили різні колонки запису | Обидві зміни зберігаються: клієнт шле тільки свої колонки. |
| Клієнт і автоматика змінили ту саму колонку | Виграє те, що останнім доїхало до власника. Автоматика може перезаписати правку наступним проходом. |
| Два клієнти змінили ту саму колонку | Так само: хто пізніше доїхав, той виграв. |
| Клієнт змінив запис, власник його видалив | Видалення виграє. Клієнт отримує tombstone, правка зникає з повідомленням. |
| Клієнт видалив запис, власник його змінив | Видалення виграє. |
| Клієнт створив запис, батька якого власник видалив | Створення відкидається разом із залежними. |
| Клієнт створив запис, що порушує унікальний індекс на бізнес-полі | `Rejected: unique`, запис залишається в репліці з позначкою помилки (відкрите питання 2). |

Base version, синхронізація годинників і ручне злиття не потрібні: на власнику немає ручних правок, з якими можна було б конфліктувати.

## 10. Tombstones: коли видаляти

### 10.1 Що накопичується

| Записи | Накопичуються | Коли зникають |
|---|---|---|
| `SyncVersion`, `SyncBase`, `SyncMask` у живих рядках | Ні, по одному значенню на рядок, перезаписуються | Разом із записом |
| `_sync_client_cursors`, `_sync_floor` | Ні, рядок на клієнта й таблицю | Разом з клієнтом |
| `_sync_tombstones` | Так, batch delete на 100k лишає 100k рядків | За правилами нижче |
| `_sync_clients` | Ні, рядок на клієнта | Після терміну зберігання без підключень |
| `_sync_outbox` на клієнті | Тільки поки є невідправлені дії | Після підтвердження власника |

### 10.2 Правила очищення на власнику

Фонова задача раз на годину, видаляє пачками по ~1000 рядків короткими транзакціями, щоб не тримати writer-а і не заважати автоматиці.

1. **Після підтвердження всіма клієнтами.** `floor = MIN(acked_version)` серед клієнтів, яких бачили за термін зберігання. Tombstones з `version ≤ floor` більше нікому не потрібні. Якщо клієнтів нема зовсім, усі tombstones можна видалити: новий клієнт однаково почне зі знімка.
2. **За терміном.** Tombstones з `deleted_at` старше терміну зберігання видаляються незалежно від підтверджень. Термін налаштовується, за замовчуванням **30 днів**.
3. Клієнти з `last_seen` старше терміну видаляються з `_sync_clients` і `_sync_client_cursors`. Клієнти з `last_seen` старше за вікно активності (24 год) не враховуються у `_sync_floor`, але лишаються в таблицях до терміну зберігання.
4. При кожному видаленні `_sync_meta.purged_version` піднімається до найбільшої видаленої версії.

При одному активному клієнті tombstones зникають майже одразу після того, як він їх отримав.

### 10.3 Клієнт, що відстав

Handshake порівнює мінімальний курсор клієнта з `purged_version`. Якщо курсор менший, частина видалень уже забута, і клієнт отримує `SnapshotRequired`:

1. Агент спершу відправляє чергу дій (Apply не залежить від курсора).
2. Завантажує знімок. Поки він їде, користувач може далі працювати зі старою реплікою, нові дії йдуть у її чергу.
3. Перед підміною файлу дії, що лишились у черзі, переносяться в нову репліку разом зі значеннями: для створення весь рядок, для патча перелічені колонки, для видалення рядок видаляється в новій репліці. Без перенесення значень дія зі старої черги відправила б уже стан зі знімка, а не правку користувача.

Ціна: клієнт, що був без зв'язку довше за 30 днів, перезавантажує сотні МБ. Це прийнято.

### 10.4 На клієнті

Чистити майже нічого: дія зникає з черги після підтвердження власника, tombstones не зберігаються (отримав, видалив запис, забув).

## 11. Перенесення даних на клієнт (звільнення місця на власнику)

Користувач хоче забрати частину даних інстансу собі і видалити їх на власнику, щоб лишилась одна копія, у клієнта.

Звичайне видалення тут не годиться: власник створить tombstones, вони приїдуть у репліку, і записи зникнуть і в клієнта. Тому дані спершу копіюються в окреме сховище клієнта, яке синк не чіпає, і тільки потім видаляються на власнику.

### 11.1 Архів

- На клієнті для кожного інстансу є файл архіву `X.archive.db` з тією ж схемою, без службових таблиць синку. Він належить клієнту, власник про нього не знає.
- Архів бере участь у шарі злиття як ще одне джерело з позначкою "архів інстансу X". Записи в ньому користувач бачить і фільтрує разом з рештою.
- Записи архіву редагуються локально, як дані local.db, і більше нікуди не відправляються.

### 11.2 Як виконується

1. Користувач вибирає інстанс і фільтр, наприклад "записи, старші за 2025 рік", і бачить, скільки записів і скільки місця це звільнить.
2. **Перевірка стану.** Перенесення доступне тільки коли інстанс на зв'язку, повністю досинхронізований і черга дій порожня. Інакше в репліці може не вистачати дочірніх записів або свіжих версій.
3. **Замикання по FK.** До вибраних записів рекурсивно додаються всі дочірні, бо каскад на власнику видалив би їх разом з батьком. Записи, на які вибрані посилаються (довідники, батьки), копіюються в архів як довідкові, але на власнику не видаляються.
4. **Копіювання.** Одна транзакція на архів: рядки з репліки переносяться в `X.archive.db` разом з `SyncVersion`. Після коміту копія надійна.
5. **Черга.** У тій же логічній операції в чергу репліки йде одна дія `kind = 4` з предикатом (умова вибору плюс замикання по FK, виражене як умова на батьківські ключі) і версією V, до якої репліка повна (8.6). Якщо умову не виразити предикатом, дії йдуть по одній на запис з `expected_version`.
6. **Власник** виконує `DELETE ... WHERE SyncVersion <= V AND <умова>`, каскад по FK прибирає дочірні. Рядки, які автоматика встигла змінити після V, лишаються; їх ключі повертаються як `Rejected: changed`, клієнт перекопіює свіжі версії в архів і повторює.
7. Tombstones повертаються в репліку звичайним шляхом і прибирають записи з неї. Копія в архіві лишається.

Падіння на будь-якому кроці безпечне: копія робиться до видалення, повторне копіювання перезаписує рядок, повторне видалення вже видаленого нічого не ламає.

### 11.3 Кілька клієнтів

Tombstones перенесення приїдуть і до інших клієнтів цього власника, і в них записи зникнуть з реплік. Єдина копія залишиться в архіві клієнта, який виконав перенесення. Для одного клієнта це те, що треба; для кількох це треба показати в діалозі підтвердження.

### 11.4 Що бачить користувач

- Діалог: кількість записів, скільки з них дочірніх, скільки місця звільниться на власнику, попередження, що копія буде тільки на цьому комп'ютері.
- Прогрес: "скопійовано 40 000 з 100 000", далі "видалено на інстансі 12 000 з 100 000".
- Записи, яких власник не видалив через зміну, автоматично перекопіюються. Якщо після кількох спроб запис усе ще змінюється (автоматика активно з ним працює), він лишається на власнику і потрапляє в список повідомлень.

### 11.5 Повернення місця на диск власника

`DELETE` у SQLite не зменшує файл, звільнені сторінки лише позначаються вільними.

- Повний `VACUUM` переписує весь файл, на час роботи блокує запис і потребує ще стільки ж вільного місця. Для сотень МБ це хвилини простою автоматики.
- Тому БД власника переводиться в `auto_vacuum = INCREMENTAL` (одноразово, потребує одного повного VACUUM при міграції). Після перенесення фонова задача викликає `PRAGMA incremental_vacuum(N)` невеликими порціями сторінок короткими транзакціями, і файл зменшується поступово, не заважаючи автоматиці.
- Tombstones перенесення очищаються за звичайними правилами розділу 10. Вони займають десятки байт на запис, тобто 100 000 перенесених записів дають кілька МБ, які зникнуть після підтвердження клієнтом.

## 12. Що бачить користувач

**Статус інстансу** (у списку інстансів і над таблицею, де є його дані):

| Стан | Як показано |
|---|---|
| Завантаження знімка | "Завантаження, 42 %". Дані інстансу ще не показуються, інші працюють. |
| Досинхронізація | "Дані станом на 14:05, лишилось 38 000 змін". Таблиця оновлюється на очах. |
| Синхронно | Зелена позначка, без тексту. |
| Нема зв'язку | "Нема зв'язку з 14:05". Дані доступні, правки йдуть у чергу. |
| Несумісна версія | "Оновіть додаток на інстансі або клієнті". |

**Невідправлені зміни**
- Лічильник на інстансі: "12 змін очікують відправки".
- Позначка на рядку, для якого є дія в черзі. Шар злиття позначає такі рядки за `_sync_outbox`.

**Канал не встигає.** Якщо відставання таблиці (голова власника мінус курсор, у рядках) росте три хвилини поспіль, статус інстансу змінюється з лічильника на попередження: "канал не встигає: відстаємо на N змін, росте". Користувач має розуміти, що це не пауза, а недостатня пропускна здатність; найновіші рядки при цьому видно, повна репліка з'явиться, коли навантаження спаде.
- Видалені локально записи зникають одразу, а в статусі видно "видалення 12 000 записів очікує відправки".

**Відкинуті дії** збираються в список повідомлень по інстансу: запис, причина, час. Наприклад "правку запису X втрачено: його видалено на інстансі" або "не збережено: батьківський запис видалено".

## 13. Читання: шар злиття

- Запит описується як функція "дай контекст, поверну IQueryable". Шар злиття викликає її для local.db і кожної репліки окремо, бо запит, побудований на одному DbContext, не виконується на іншому.
- Фільтр виконується в кожній репліці SQLite, повторно в пам'яті не фільтрується.
- Довантаження при прокрутці: "дай N рядків після останнього показаного" за парою (поле сортування, Id). Кожне джерело віддає свої N після ключа, шар злиття вибирає з них перші N. Якщо зараз довантаження зроблене через `Skip(K)`, його треба перевести на цей спосіб.
- Кількість записів це сума по джерелах. Суми і групування потребують окремої логіки злиття на кожен вид.
- Запити до джерел ідуть паралельно, кожне на своєму з'єднанні в WAL і не блокує агентів.

## 14. Помилки та відновлення

| Що сталося | Що відбувається |
|---|---|
| Обрив потоку Subscribe | Агент перепідключається з експоненційною затримкою, `Start` з поточними курсорами і відрізками. Власник продовжує з тієї ж прогалини; якщо щось і прийде повторно, рядок відкидається правилом версій. |
| Обрив під час знімка | Продовження з того ж зміщення. Якщо власник уже видалив тимчасовий файл, знімок починається заново. |
| Відповідь Apply втрачена | Повторна відправка, власник пропускає дії за `applied_seq`. |
| Клієнт упав посеред застосування пачки | Транзакція відкочена, курсор не зсунувся, пачка приїде знову. |
| Власник упав посеред Apply | Транзакція відкочена, `applied_seq` не змінився, клієнт відправить знову. |
| БД власника замінили з бекапу | Власник на старті бачить, що версія в БД менша за записану поза нею, і генерує новий `instance_id` (5.3). Handshake вимагає знімок. Додатково handshake ловить `cursor > version`. |
| Різні версії схеми | Синк зупиняється, черга зберігається. Після оновлення обох сторін клієнт бере новий знімок з перенесенням черги. |

## 15. Міграція існуючих БД

1. **GUID замість автоінкременту.** Одноразова міграція для таблиць з цілим PK: додати колонку GUID, заповнити, переписати FK-колонки дочірніх таблиць через join, перебудувати таблиці. Виконується до першого увімкнення синку. Треба з'ясувати, чи цілі ID десь видно назовні (відкрите питання 3).
2. **SyncVersion і службові таблиці.** Звичайна EF-міграція. Перший старт після неї ставить усім рядкам унікальні версії одним проходом і створює тригери.
3. **Подальші міграції схеми.** Перебудова таблиці копіює `SyncVersion` як є, тригери перестворюються при старті. Зміни даних у міграціях не версіонуються, але після оновлення клієнт однаково бере новий знімок через зміну версії схеми.

## 16. Продуктивність

Оцінки, не виміри на реальній схемі:

| | Оцінка |
|---|---|
| Нові записи на інстансі | до ~10/с, з пов'язаними і змінами до ~100 рядків/с |
| Місце на власнику | колонка плюс індекс, ~15–20 байт на запис |
| Запис на власнику з тригерами | приблизно у 2–3 рази повільніше на insert і update |
| Застосування пачками на клієнті | 20 000–50 000 рядків/с на файл |
| Трафік онлайн з одного інстансу | ~20 КБ/с до стиснення, ~5 КБ/с після, якщо все їде повними рядками; при типовій зміні однієї-двох колонок у рядку на 200 байт частковий рядок це 30–40 байт, тобто у 5 разів менше для оновлень |
| Місце на власнику під базу і маску | ще ~2–10 байт на рядок (varint) |
| Досинхронізація 100 000 змін (~5 МБ стиснено) | ~40 с на 1 Мбіт/с, ~2,5 хв на 256 кбіт/с, ~10 хв на 64 кбіт/с |

Вузьке місце при цьому темпі канал, а не диск. На слабкому каналі допомагає схлопування: чим довше відставання, тим більше проміжних змін не їде взагалі.

**Перший крок реалізації це вимір** на копії реальної БД: сповільнення запису власника з тригерами, швидкість застосування пачок на клієнті, розмір знімка після стиснення. Разом з ним стенд мережі на `tc netem`: затримка 1,5 с в кожен бік, 2 Мбіт/с вниз, 70 кбіт/с вгору. Критерій: потік Subscribe забирає не менше ніж 80 % каналу вниз з вибраним вікном HTTP/2, і з'ясовано, чи достатньо динамічного масштабування вікна в .NET.

## 17. Тестування

- **Тригери**: згенеровані для кожної таблиці; insert, update, delete, каскадне видалення, ExecuteUpdate/Delete на 100k, перебудова таблиці міграцією; маска змінених колонок, зсув бази при `floor ≥ OLD.SyncVersion`, накопичення маски при двох клієнтах на різних курсорах.
- **Поколонкові оновлення**: клієнт біля голови отримує тільки змінені колонки; клієнт поза вікном активності отримує повний рядок; рядок, вставлений і змінений до першого Ack, їде повним; `NeedFull` після втрати рядка в репліці; після повного синку репліка дорівнює власнику при будь-якій суміші повних і часткових рядків.
- **Збіжність**: випадкова послідовність дій автоматики на власнику і дій користувача на клієнті, частина офлайн, з випадковими обривами. Після повного синку репліка дорівнює власнику, а відкинуті дії пояснені.
- **Обриви**: посеред знімка, посеред досинхронізації з кількома відрізками (продовження без повторів), втрачена відповідь Apply, правка запису, дія якого в дорозі.
- **Канал**: на стенді з `netem` інтерактивна правка за імпортом 10k доїжджає за час однієї пачки; порожня репліка показує перші рядки за секунди; склеювання онлайн-пачок не збільшує p95 понад RTT + 0,5 с.
- **Зміни під час досинхронізації**: записи, створені під час довгої досинхронізації, приїжджають у наступній пачці; злиття відрізків і підняття курсора; ліміт відрізків досягнуто; потік змін стабільно швидший за канал: стан курсора обмежений, статус показує зростання відставання.
- **FK**: офлайн ланцюжок A → B → C, видалення A на власнику до відправки, патч, що переводить FK на новий запис з черги.
- **Очищення**: клієнт відстав менше і більше терміну зберігання; перенесення черги в новий знімок.
- **Лічильник**: старт з 2³¹ + 1, щоб зловити 32-бітне число на будь-якому шарі; відкат БД власника з бекапу.
- **Перенесення в архів**: глибокий ланцюжок FK, зміна запису автоматикою між копіюванням і видаленням, падіння клієнта між кроками.
- **Продуктивність**: вимір з розділу 16, повторюваний на CI на фіксованому наборі даних.

## 18. План реалізації

1. Вимір на копії реальної БД і стенд мережі з `netem` (вікно HTTP/2).
2. Міграція PK на GUID.
3. Трекінг на власнику: `SyncVersion`, службові таблиці, генератор тригерів, налаштування EF.
4. gRPC: Snapshot і handshake як перше повідомлення Subscribe; на клієнті завантаження і перетворення на репліку, порожня репліка.
5. Subscribe: досинхронізація з пріоритетами, онлайн, застосування на клієнті.
6. Шар злиття і перехід UI на нього, keyset-довантаження.
7. WriteRouter, черга з класами дій, Apply з адаптивною пачкою, предикатні масові дії, обробка відкинутих дій.
8. UI станів і невідправлених змін.
9. Очищення tombstones, обробка клієнта, що відстав.
10. Перенесення в архів і incremental vacuum на власнику.

## 19. Відкриті питання

1. **Перелік таблиць.** Які саме таблиці реплікуються, а які ні, і де зараз автоінкремент. Потрібен DbContext або список таблиць.
2. **Унікальні індекси на бізнес-полях** (код, назва) окрім PK. Якщо є, офлайн-створення на клієнті може зіткнутися з записом, створеним автоматикою. Що робити: відкидати з повідомленням (так зараз у дизайні) чи зливати із наявним записом?
3. **Зовнішні посилання на цілі ID.** Чи видно числові ID в UI, експортах, інтеграціях? Від цього залежить, чи треба зберегти старий ID окремою колонкою після міграції на GUID.
4. **Local.db клієнта.** Припущення: клієнт має власні дані і бере участь у злитті як ще одне джерело. Підтвердити.
5. **Спільний компонент читання.** Чи читають таблиці UI через один компонент, чи запити розкидані по екранах? Від цього залежить обсяг переведення на шар злиття.
6. **FK на клієнті під час досинхронізації.** Чи прийнятна відмова локальної правки з "дані ще синхронізуються", коли батько рядка ще не приїхав? Альтернатива: вимкнути FK у репліці повністю і емулювати каскад у WriteRouter.
7. **Скасування невідправленого видалення.** Зараз видалення локально фізичне, тож скасувати його до відправки можна тільки з повторним отриманням рядків з власника. Чи потрібна кнопка "скасувати" для черги?
8. **Термін зберігання tombstones.** 30 днів за замовчуванням. Чи є клієнти, що довго бувають офлайн і для яких повний знімок занадто дорогий?
9. **Шумні таблиці.** Які таблиці в UI оновлювати з затримкою і з якою частотою.
10. **Пріоритет видимих рядків за ключами** і **фільтр на власнику**. Додаємо, якщо вимір покаже, що пріоритету відкритих таблиць недостатньо на реальному каналі.
11. **Архів і бекап.** Після перенесення архів це єдина копія даних. Чи має додаток сам робити його резервну копію, і чи потрібна зворотна операція "повернути з архіву на інстанс"?
12. **Безпека.** Коли знадобляться TLS і автентифікація клієнта, і чи має власник обмежувати, які клієнти можуть писати.
13. **Ширина таблиць для маски.** Чи є таблиці з понад 63 колонками (тоді маска `BLOB`), і яке вікно активності клієнтів ставити: 24 години за замовчуванням, але якщо клієнти регулярно зникають на кілька днів, маски для решти ростуть.
14. **Потік даних понад пропускну здатність каналу.** Межа за симуляцією ~4 800 рядків/с на клієнта при 2 Мбіт/с, ~480 на інстанс при десяти. Наперед невідомо, яка таблиця отримає навантаження, тому виключати таблиці з реплікації або читати їх з власника на запит не планується: репліка досинхронізується, коли навантаження спаде, а користувач бачить попередження (розділ 12). Лишається з'ясувати виміром, чи буває стійке перевантаження на реальних темпах і чи потрібно виносити важкі колонки окремо.
