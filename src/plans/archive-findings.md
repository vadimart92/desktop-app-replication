# Archive findings (snapshot install) — deferred

Found while planning the simple snapshot import (its plan file is gone; the change is implemented in `ReplicaWriter.InstallSnapshot`). Not fixed; archive handling was out of scope for that change and these points are still open.

- **Archive key.** Archived rows have `InstanceId = "<old>:archive"` (`SyncColumns.ArchiveOf` in `SyncModel.cs`). `InstallSnapshot` deletes `WHERE InstanceId = @new` and, for Ids in the snapshot, rows of other non-archive remote instances; it never touches archives.
- **No link between a restored owner and its old instance.** The client now finds its replica by the owner's `instance_id` (`Identity` RPC), not by address, so a restored owner (new `instance_id`) is simply another instance. The old instance keeps its remaining rows, cursors, outbox and `_sync_instances` row, and `<old>:archive` rows stay under the old id; `HasArchiveBelow` and the FK rule `child == ArchiveOf(parent)` (`SyncColumns.MayReference`) see them only for the old instance. The earlier idea of renaming `<old>:archive` to `ArchiveOf(new)` no longer has an old-to-new link to work from. Nothing removes an abandoned instance yet; a `RemoveInstance` that deletes its rows, archive, cursors, outbox and `_sync_instances` row is the open piece.
- **Id clash.** (Current behaviour, not a plan.) `Id` is the sole primary key. Against another remote instance's live rows the snapshot wins (`InstallSnapshot` deletes them first), which is what lets a restored or cloned owner load. Against an archived row it is still silently skipped by `INSERT OR IGNORE`: the live row never arrives and the cursor jumps to V. A plain `INSERT` would fail the whole transaction instead. Happens for example when an owner backup restored later contains rows the client archived after the backup. Needs a policy: archive wins (current) or snapshot wins.
- **Dangling children.** The install uses a bare `DELETE` with foreign keys off, not `ArchiveGuard.DeleteOrArchive` (which the stream-tombstone path uses). A parent that archived rows point to and that is missing from the new snapshot is deleted, and the archived children dangle. The new delete of another instance's rows with the same Ids has the same effect on that instance's archive.
- **Pending Archive actions.** Once the outbox of the installed instance is dropped at snapshot time, an unsent `Archive` action is dropped too. The outbox of an old instance (restored owner) is not dropped: it stays, never sent. The owner may still hold those rows, so they arrive live in the snapshot while the archived copy also exists (Id clash above). The in-memory `_archiveRetry` / `_archiveTries` in `SyncAgent` also refer to rows the install replaced.
- **Not verified by running code.** All of the above comes from reading `ReplicaWriter.cs`, `ArchiveGuard.cs`, `SyncModel.cs` and `SyncAgent.cs`.
